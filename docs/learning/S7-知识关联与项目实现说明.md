# S7｜从历史观测到七日预测：知识关联与项目实现

本阶段把 Python、机器学习、数据库和网页串成一条可以实测的链路。预测对象是一个城市每天的 **0–10拥堵指数**，它是道路拥堵程度的代理指标，不是车流量或通勤人数。目前演示数据由固定种子生成，标为 synthetic_test；演示误差不能代表真实城市交通预测准确率。

Python 先做“整理日历”。已有 S5 ETL 负责检查原始字段、时间、来源和批次，成功后写入 MySQL；S6 准入函数再核对提交事实与逐条血缘。S7 复用它取得可靠输入，按 UTC 日历把同城市、同数据集、同版本的 CITY 观测求日均。一天至少覆盖四个时段，缺日或样本不足时拒绝训练。这样既不会把道路和城市混在一起，也不会把“没有数据”变成零拥堵。

机器学习不能直接理解日历序列，所以需要“特征工程”：把昨天、七天前、十四天前、二十八天前的拥堵指数，以及此前一周/四周均值、一周波动、星期和年周期，整理成一行输入。最关键的是时间方向：预测某天时，只能使用这一天之前已经知道的数值。滚动均值不包含目标当天；不先在全数据上拟合补缺或标准化器。

随机森林像多个独立评委：每棵决策树从部分训练样本学习条件，最终平均各树结果，减少单棵树的偶然误差。XGBoost则让后续的小树逐步修正前面模型的误差。项目还保留两个简单但必要的对照：未来都等于最后一天的 naive，以及沿用上周同星期数值的 seasonal7。复杂模型如果没有明显优于最佳基线，就回退基线，不为了展示算法而强行使用复杂模型。

“时序回测”是把过去当作未来来演练。项目把最后56天顺序分为28天验证和28天测试，每部分有四个七日起点。每次只能看到起点之前的历史，先训练，再连续预测未来七天。预测第二天时，昨天的输入来自第一天的预测；不能偷看第一天真实值。验证集决定选择哪种模型，独立测试集只负责报告误差。MAE是误差绝对值的平均，RMSE会更重地惩罚较大的误差，两者单位都是拥堵指数。最后用截至数据截止日的全部历史重新训练，输出连续七个日历日。

MySQL保存结果与证据，而不是在网页请求中训练模型。离线Python CLI生成模型文件、输入与配置哈希、回测报告及七点预测，发布时重新核验已提交数据，并用可信代码独立重训、重算回测和七日推理，逐点比较后才发布。即使只把一个预测改成另一个合法值也会拒绝，且不加载外部提交的joblib对象。发布先准备STAGING任务，再把七点、评估及当前指针一起提交；中断或失败时旧版本继续可见。相同任务重试不重复写入，旧任务不能覆盖新任务。预测使用自己的发布指针，不改变S6数仓当前版本。

Java Spring Boot负责只读查询：`/api/v1/predictions` 在同一事务快照中读取当前已发布任务及明细，附上requestId、来源和UTC时间。OpenAPI是前后端共同的接口说明。Vue先验证响应结构和七日连续性，再交给ECharts绘图：蓝色实线是历史实际观测，黄色虚线是预测。模型版本、训练时间、生成时间、数据截止时间和合成演示限制同时展示；没有已发布模型或请求失败时显示明确状态。

V3.2增加一条研究入口：CSV/JSON → 字段检查与映射推荐 → 人工确认 → 独立的速度/流量/指数序列契约 → 质量与任务适用性 → 时序/域评估。速度先明确单位和时区，不把mph当作拥堵指数。适用性按采样周期和预测窗口计算，足够则TRAINABLE，有限历史只跑BASELINE_ONLY，不满足条件为NOT_EVALUABLE。缺失特征只向前补，标签不补。跨域实验冻结源域拟合与选模，目标域历史只提供滞后输入；同文件、同城市或高度重叠数据不能伪装迁移。

实际Zenodo文件头已检查，但下载截断，单位、时区与上游许可仍待确认，用户也明确暂不放行真实训练。深圳未获得可核验历史字段，PeMS需用户自行申请账户。因此目前两个原创合成域只证明流程能够运行，不证明真实跨城市泛化；新速度/流量研究也没有写入原CITY拥堵预测API。Python适配和模型层负责语义与评估，MySQL/Java/Vue继续承担已验证日拥堵指数的发布与展示，各层通过明确契约连接。
