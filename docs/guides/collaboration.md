# GitHub 协作规范

## 当前 V2.1 执行口径

采用项目负责人主导开发、队友异步任务交付、单一 main 主线、PR 审查与集成。负责人负责 Java、Vue、机器学习、共享契约和集成；队友其他模块按后续明确任务书分配。本轮 S2 由负责人独立完成，队友尚未参与，不阻塞 S2 技术交付；没有队友 Approved Review，`S1-COLLAB-DEBT = OPEN`。

用户已授权 S2 功能分支正常 Push、创建 PR、读取/修复/复测 CI；未授权合并 PR、推送 main、改写远程历史或更改安全设置。交付状态为 SUBMITTED_FOR_REVIEW，最终由总规划师独立裁定；CI 成功不等于审核批准或阶段 ACCEPTED。以下 S1 建立的双人审核规则用于真实协作，不将负责人独立操作伪写为已满足双人补验。

## 历史规则与持续协作

本规范从 S1 建立。本地 Git 已在 WP3-A 初始化为 main，21项代表性忽略规则测试通过；WP3-B 已完成首次提交、私有远程创建及推送。当前远程仅启用 Squash Merge，并自动删除已合并分支；分支保护 API 返回403，提示私有仓库需要 GitHub Pro，main 的 protected 为 false。因此 PR 审核目前依赖双方流程约束，不能声称已有技术强制保护；实际证据见阶段报告。首次建仓及本工作包报告同步属于用户明确授权的初始化操作，后续日常业务变更仍必须遵守下列 PR 流程。

1. `main` 为稳定分支。日常业务变更必须经过 PR 和对方审核，禁止未经审核直接推送 main。
2. 每项工作从同步后的 main 建立短生命周期分支，例如 `feat/traffic-summary`、`fix/time-bucket`、`docs/data-contract`。一条分支聚焦一个可审查任务。
3. Commit 使用 `type(scope): 简述`，如 `docs(architecture): 明确离线数据流`。常用 type 为 feat、fix、docs、test、refactor、chore；只提交与任务有关的变更，不含密钥和原始数据。
4. 使用 PR 模板说明目的、文件、验证、契约和配置影响。创建前检查差异、提交范围、敏感信息和所需验证；不能执行的检查明确说明原因。
5. 对方必须进行真实 Code Review：阅读差异，检查逻辑与边界，核对验证证据，必要时本地复核。作者回应意见并修正后再申请批准，不以形式化批准代替审查。
6. 优先使用 Squash Merge，确认目标分支、审核和验证结果后合并；合并后删除已完成的功能分支。
7. 合并后两人先保存各自未提交工作，再切回 main 并从远程同步；可使用 `git pull --ff-only` 避免意外合并。确认 main 一致后再开始下一项任务，不覆盖未保存修改。
8. contracts、database、infra 的共享改动须事先双方协商，PR 说明兼容性、迁移和配置影响；不能单方面改变字段口径。
9. 发生冲突时先确认双方变更目的，在功能分支逐处解决并重新验证，请对方复审。禁止用强制推送、重置或整体覆盖方式抹去他人工作；同步失败先沟通，不盲目重试覆盖。

远程仓库建立后，应按平台能力评估保护 main、要求 PR 和审核等设置，并记录实际生效证据。在配置前本规范仍是双方应遵守的流程，不能声称技术保护已生效。
