## 模型、迁移和技术决策

结构源：`database/migrations/V1__commute_core.sql` 与 `V2__strengthen_core_constraints.sql`。V1 Git blob 始终为 `6f47ece99fbfbe54d691b1c8672dbe3fca0aca40`，与接管 Head 完全一致。V2 是新增迁移，不使用 repair 或 baseline 绕过历史。

| 表 | 主键与关键约束 |
|---|---|
| dataset_registry | dataset_id；严格来源/许可枚举，历史及实时必须 authorized，生成来源必须 not_applicable |
| city | 小写 kebab-case 字符串 ID；来源 FK；数据库拒绝空白名称 |
| region | 城市 FK、同城复合键；坐标全空或完整 WGS84 三字段，拒绝全部部分 NULL 组合 |
| road_segment | 城市/区域同城 FK；允许同名不同路段，以 ID 区分；保留城市名称查询索引 |
| traffic_observation | 数据集/城市/目标关联；目标与同城 FK；源+目标+时刻唯一；速度/指数范围及采集时间顺序 |

DATETIME(3) 使用 UTC 语义；速度 km/h、0～250；拥堵指数标准化 0～10。原始来源不同单位、缺失指标和采样窗口不能直接混合；S4 必须明确转换/拒绝策略，不允许用零填充冒充观测。S3 无通勤人数、OD 或真实预测结果。

Flyway 在同一主版本内从 BOM 11.7.2 调整为 11.20.3，core/mysql 模块统一。旧源码的测试版本上限为 8.1，新源码为 9.4，依据 [官方 11.20.3 MySQL 实现](https://github.com/flyway/flyway/blob/flyway-11.20.3/flyway-database/flyway-mysql/src/main/java/org/flywaydb/database/mysql/MySQLDatabase.java)。本机迁移日志不再出现 MySQL 8.4 超出该 Flyway 测试版本范围的警告；这不替代官方支持承诺。V2 使用的 BINARY expr 在 MySQL 8.4 有弃用提示，当前行为已验证；未来调整必须新增迁移，不能改已应用的 V2。

## 测试隔离与错误边界

`scripts/s3_database.py` 仅对已授权的回环 MySQL 创建新随机 s3test_<UUID> 库和随机 s3t_ 账号。GRANT 对库名下划线转义；账号无全局权限，不具备其他库权限。密码只传子进程；准备器不清理或复用持久库。

`IsolatedMySql` 是仅测试编译的配置。TEST_DB_* 不回退 DB_URL；JDBC URL 严格限制为回环地址和唯一允许的参数，拒绝 createDatabaseIfNotExist 等副作用选项。禁用其他 SQL 初始化。FlywayMigrationStrategy 先读取实际 DATABASE()/CURRENT_USER()/@@server_uuid，全部匹配后才迁移，修复原 @BeforeAll 检查太晚的问题。

真实 Spring 启动负测覆盖错误预期数据库身份、错误服务器 UUID、指向普通库的 JDBC URL；均要求非零退出、指定保护异常、目标库仍为零表，不能以编译失败冒充保护通过。正确设置后成功迁移。第二轮使用新库再次跑完整套件，保留第一轮数据而不清空。

后端读取真实 MySQL，Repository 参数化 JOIN 和稳定排序，Service 聚合来源，Controller 保留 S2 两接口/错误封套/请求 ID。空目录为 database_catalog/null；混合来源为 mixed_catalog/null。dataAsOf 始终 null。实际 JDBC 握手超时经真实 HTTP 返回安全 503，不使用 Service/Repository 替身；其他 500/显式 503 的替身测试仍明确标记，不能混作数据库故障证据。/health 为 liveness，不是数据库 readiness；启动阶段数据库不可用时 Flyway 会阻止启动。

Vue 客户端验证契约；TypeScript 元数据使用可辨识联合类型关联 sourceType/datasetId；页面区分全部七类来源及空/混合目录。来源登记不是授权真实性证明；本阶段所有输入均为合成数据，不宣称获得真实交通观测。

## 故障及最终处理

- 原 WP0：坐标 CHECK 的 UNKNOWN 漏检、ID 不严格、路名唯一不合理、测试库检查太晚。由新增 V2、迁移前实际身份校验及新库准备器处理。
- 本机首次 bootstrap 发现 skip-name-resolve 下 root@localhost 无法通过 TCP 回环登录；仅调整新实例配置并重启该实例，随后立即设置生成口令。未改已有实例。
- 真实 MySQL 同时存在两条许可约束时报告 ck_dataset_provenance；修正测试预期并核验 3819 和具体约束名。
- Flyway ErrorCode 为接口，测试编译时不能调用 enum name()；改用实际错误码文本核验 CHECKSUM_MISMATCH，保留负测。
- 浏览器自动刷新恰逢空模式重启时，原驱动把代理 502 误标成 Java 响应；增加明确 empty-restarting 阶段，仅允许无 Java 请求 ID 的代理失败，保留常规阶段全部成功响应、Java 日志关联和两接口断连检查。增加错误阶段标记的反向校验，不关闭验证器。

- 云端首轮 Run 39184765862 在准备阶段失败：Ubuntu 预装 MySQL 8.0 客户端源码没有 --no-login-paths，而 Windows 8.4 支持该选项。改用两个版本都支持的 MYSQL_TEST_LOGIN_FILE 指向独立不存在路径，并保持 --no-defaults，避免读取用户登录文件；本机新库准备器已复测，云端完整回归另行核实。诊断仅输出 MySQL 数字错误码/SQLSTATE，不输出认证内容。
